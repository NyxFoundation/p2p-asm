# x86-64 backend

The Linux x86-64 backend translates existing p2p-asm routines into scalar native
instructions. It uses LeanAsm's typed x86-64 instructions, GNU emitter, and
System V AMD64 frame helpers. There is no interpreter, QEMU dependency, SIMD
requirement, or SHA instruction requirement in the generated code.

**This translation is unproved.** RV64 theorems do not establish x86-64
correctness. The backend does not add missing protocol functionality or provide
a complete network server. Windows, macOS, and 32-bit x86 are not targets.

## Build and call

Install the pinned Lean toolchain through elan, GCC, and GNU binutils. From the
repository root on Linux x86-64:

```sh
lake build
mkdir -p build/x64
lake exe libp2p-asm-codegen --target x86_64 asm quic-decode > build/x64/quic-decode.S
gcc -Wall -Wextra -Werror -fPIE -pie -Iinclude Examples/X64.c build/x64/quic-decode.S -o build/x64/example
build/x64/example
```

The example decodes the bytes `40 25` as 37 and exits zero. All 96 routine names
listed by `libp2p-asm-codegen --help` accept `--target x86_64 asm`. Without
`--target`, output remains RV64. `--target rv64` selects it explicitly.
`hex` and the `eval*` model commands remain RV64-only; requesting x86-64 `hex`
fails rather than returning RV64 bytes.

Each emission exports `protocol_entry`. Generate one routine per library; the
command does not assign distinct public symbols for linking several emissions
into one library. Generated code supports PIE and shared libraries without
absolute text relocations.

## C boundary

Include [`include/p2p_asm.h`](../include/p2p_asm.h):

```c
struct p2p_asm_registers {
    uint64_t x[32];
};
uint64_t protocol_entry(struct p2p_asm_registers *registers);
```

This is a System V AMD64 function taking one pointer, not an ordinary C signature
with each protocol argument passed separately. The context retains the existing
routine contracts, including eight argument slots and multiple result slots:

| Context | Meaning |
| --- | --- |
| `x[0]` | Zero register; normalized to zero on entry, writes ignored |
| `x[1]` | Return sentinel; initialize to zero |
| `x[2]` | Top of a caller-owned, writable, 16-byte-aligned stack buffer |
| `x[10]` through `x[17]` | Existing `a0` through `a7` arguments and results |
| Other slots | Existing temporary and callee-saved virtual registers |

Native `rbx`, `rbp`, and `r12` through `r15` are preserved independently of the
virtual register slots. The native stack holds only the adapter frame; protocol
stack accesses use `x[2]`. Stack-free leaves such as varint codecs do not require
a stack buffer. For other routines, allocate the stack/workspace sizes required
by that routine's existing ABI documentation under `Tests/`.

The native return value is separate from the routine's result in `x[10]`:

- `P2P_ASM_RETURNED` (0): the routine returned to its sentinel. Inspect the
  routine's status/results in the context.
- `P2P_ASM_BAD_PC` (1): an invalid indirect target, fallthrough past the image,
  or a sentinel inside the image. Discard partial results and memory changes.

## Memory and control-flow constraints

The caller must provide a valid, writable 256-byte context. It must be disjoint
from every input, output, workspace, and protocol-stack buffer. Follow each
routine's existing size, alignment, permission, and aliasing preconditions.
All data pointers are real process addresses. The generated function does not
allocate buffers or translate data addresses.

This is native code, not a memory sandbox. The instruction model's region and
alignment checks are not runtime checks in this backend. Invalid memory access
can fault or corrupt memory; a bad pointer does not produce `P2P_ASM_BAD_PC`.
There is no execution-fuel limit.

Internal code addresses retain RV64 coordinates: instruction `i` has address
`0x10000 + 4*i`, regardless of the native code's load address or instruction
lengths. `AUIPC` and link registers use these coordinates. The initial `x[1]`,
with bit zero cleared, must be outside this virtual image. Zero is the normal
choice. These code addresses are not native data pointers.

Direct branches use generated labels. Indirect jumps clear bit zero, recognize
the saved entry sentinel, and check alignment and image bounds before indexing
a relative jump table. Native jump targets come only from this read-only table.
The table's relocations are resolved by GNU tools, so this backend exposes
assembly emission rather than Lean-produced final x86 machine-code bytes.

The initial implementation stores virtual registers in the context. It favors
shared routines and testable semantics over throughput; no performance or
constant-time guarantee is made.

## Verification

With Python 3.12+ on Linux x86-64:

```sh
python3 Tests/X64/check.py
```

The test command builds its Lean probes and uses temporary artifacts. It checks:

- PIC generation and linking of every public routine, the C example, CLI
  rejection paths, and preservation of the default RV64 target;
- all 33 accepted instruction operations against the RV64 model and independent
  Python arithmetic, including zero divisors, high multiplication, signed
  comparisons, shifts, memory operations, and control flow;
- zero-register behavior, source/destination aliases, signed memory offsets,
  nested internal calls, invalid PCs, and native callee-saved registers;
- QUIC/uvarint encoding, decoding, truncation, rejection, and guard bytes;
- existing QUIC wire, stream/multistream/Ping, SHA-256/512, HMAC, HKDF, and TLS
  label fixtures, comparing all 32 registers and every memory-region byte
  against the existing model/specification/reference snapshots.

Other public routines are generation/link tested, not individually executed by
this suite. Snapshot runners map fixtures only with `MAP_FIXED_NOREPLACE` and
mark read-only regions with `mprotect`. `--skip-snapshots` runs the shorter
instruction/codec/CLI suite. Tests do not establish a correctness proof or extend
the existing RV64 proof claims.
